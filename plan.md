# DLR-UT World-Model Demo — Implementation Plan (Short Sprint)

Status: September 2026. Goal: build a working, interactive demo within a few days that uses the public **DLR-UT dataset** (AIM Research Intersection, Braunschweig) to demonstrate the value of a generative "Traffic World Model" — usable both for grant applications/reviewers and for industry-partner conversations.

## ⚠️ Instructions for implementing with Claude Code (read first)

This project is implemented in **two separate phases on two different machines**:

- **Phase A — laptop, no GPU:** build the complete codebase (data pipeline, model code, FastAPI backend, browser UI) and make it end-to-end runnable and browser-testable via **mock inference**. **Do not run real model training.**
- **Phase B — VM with GPU (8× V100):** the actual training on the full real data only happens here.

**If you (Claude Code) are handed this `plan.md` on the laptop, it automatically means: you are in Phase A.** Work exclusively on the tasks under "Phase A" in section 6. A brief **sanity check** of the training script with tiny dummy data (a few rows, 1–2 iterations, CPU, just to catch code errors) is allowed — this is **not** real training and runs in seconds. Not allowed: multi-epoch training on the real DLR-UT data, downloading/installing GPU/CUDA packages, or trying to "just let the training loop run to see what happens." Once all Definition-of-Done items from section 6 are met at the end of Phase A: **stop and tell the user the repo is ready to be cloned onto the GPU VM.** Do not run Phase B on your own, not even as a test.

How to tell which machine you're on, if unclear: check `nvidia-smi` or `torch.cuda.is_available()`. No GPU detected → Phase A. GPU detected (the 8×V100 VM) → Phase B, see section 6.

## 0. Objective & deliberate scope

**What the demo shows:** from a briefly observed real traffic situation at the AIM intersection (a few seconds of real DLR-UT trajectories), a generative world model trained on your data produces several plausible, physically consistent continuations of the scene — visualized as an interactive bird's-eye-view map animation contrasting "Real" against "variants generated by the model." A stretch goal additionally shows controllable generation ("what if pedestrian X crosses anyway / vehicle Y brakes harder").

**Deliberately NOT part of this sprint:** photorealistic video generation (Cosmos-class pixel world models) as the core piece. Reason: these models require Ampere-or-newer GPUs (your 8×V100s are not sufficient per the vendor docs) and are too heavyweight for a few-day sprint. Instead: a **trajectory world model** — an equally current but far more lightweight model class that runs on V100 without restriction. Photorealistic clips are sketched below as an optional stretch goal via a hosted API, not as a core dependency.

## 1. Why this scope is the right choice for "a few days"

- **DLR-UT only, not DLR-HT:** the intersection offers dense multi-agent interaction (cars, bikes, pedestrians) in a tight space — visually and substantively sharper for a short demo than pure highway longitudinal trajectories, and with a direct link to VRU safety (pedestrians/cyclists), a topic with high funding and industry relevance.
- **Trajectory- instead of pixel-world-model:** generative diffusion models over trajectory sequences (methodological lineage: NVIDIA's own [NVlabs/CTG](https://github.com/NVlabs/CTG) "Guided Conditional Diffusion for Controllable Traffic Simulation", as well as Trajectron++/Trajeglish as related approaches) are themselves recognized, cited state-of-the-art research on "traffic world models" — just at the trajectory level rather than the pixel level. They are small (typically 1–10M parameters), need no Ampere architecture, and can be trained in hours rather than days.
- **BEV map animation as the UI:** robust, quick to build, understandable within seconds for laypeople (grant reviewers, industry managers) AND informative enough for an expert audience.
- **Laptop/VM split:** the complete code (pipeline, model, backend, UI) can be written without any GPU and fully tested in the browser via mock inference — only the actual training run needs the V100 VM. This decouples "code finished & UI visible" from "model trained" and makes Phase A completely independent of VM availability.

## 2. Technical approach: model choice

**Reference method:** [NVlabs/CTG](https://github.com/NVlabs/CTG) (NVIDIA Research) serves as the methodological blueprint — diffusion over short multi-agent trajectories, conditioned on observation history and optionally steerable via guidance terms (e.g. collision avoidance, goal adherence).

**Key decision:** porting the full CTG repo 1:1 is an avoidable risk for a few-day sprint — it is tightly coupled to nuScenes (map format, `trajdata` dependency), uses old pinned versions (PyTorch 1.11, CUDA 11.3), and brings extra complexity (STL guidance, optional ChatGPT integration) you don't need.

**Recommendation:** a **lean, custom implementation following the same principle**, tailored to the DLR-UT format from the start — with a clear reference to CTG/Trajectron++/Trajeglish as methodological blueprints in the docs and the pitch (scientific grounding is preserved without the integration risk of the foreign codebase). Core components:

- Feature pipeline: extract short time windows (observation history + prediction horizon) per interaction scene from DLR-UT
- Model: transformer or 1D-conv backbone + diffusion sampling head over the future position deltas of all agents in the scene jointly (not per agent in isolation — this is the core of what "world model" means as opposed to a single-agent trajectory predictor: a jointly consistent continuation of the whole scene)
- Conditioning optionally extensible with simple guidance terms (collision avoidance) for the "controllable generation" stretch goal

**Important for Phase A:** this model is written entirely as code in Phase A (architecture, training script, sampling function) — it just isn't trained on the real data. See section 5 for the swappable inference interface that lets the app still run in the browser.

## 4. Data basis

- **DLR-UT only** ([Zenodo](https://zenodo.org/records/13907201)), AIM Research Intersection, Braunschweig.
- Load via [TASI](https://github.com/DLR-TS/TASI):
  ```python
  from tasi.dlr import DLRUTDatasetManager, DLRUTVersion, DLRTrajectoryDataset
  dataset = DLRUTDatasetManager(DLRUTVersion.latest)
  path = dataset.load()
  ds = DLRTrajectoryDataset.from_csv(path)
  ```
  Result: a dataframe with a multi-index (timestamp, object ID); per the TASI docs, fields include bounding-box position, velocity, dimensions, and classification type (car/bike/pedestrian). Verify the exact column names/units/coordinate system in **Phase A, day 1** using the TASI example notebooks, don't assume them blindly. Downloading the DLR-UT dataset itself needs no GPU and is part of Phase A.
- **To clarify in Phase A:** is there already a map geometry available for the AIM intersection (lanes, intersection outline, e.g. as OpenDRIVE)? If not: reconstruct a rough one from the trajectory data itself as a fallback (see risks below).
- **To clarify in Phase A:** how many trajectories/interaction scenes does the one published Zenodo tag actually contain? This determines whether the data volume is sufficient for robust model training or whether augmentation is needed (see risks).

## 5. Demo architecture — including a swappable inference interface

- **Backend:** Python training/inference scripts; for the live demo, a small local service (e.g. FastAPI) that samples new variants on request and delivers them to the UI as JSON (trajectory coordinates over time).
- **Core idea for the phase transition — a single swappable interface:**
  ```python
  class VariantGenerator(ABC):
      def generate(self, scene_context: SceneContext, n_variants: int) -> list[Trajectory]:
          ...

  class MockVariantGenerator(VariantGenerator):
      # Phase A: produces plausible dummy variants (e.g. lightly perturbed
      # copies of the real trajectory), same return structure as the real model
      ...

  class TrainedModelVariantGenerator(VariantGenerator):
      # Phase B: loads the trained checkpoint and samples real variants
      ...
  ```
  The FastAPI service gets the implementation injected via a config/environment variable (e.g. `GENERATOR_MODE=mock` vs. `GENERATOR_MODE=trained`). This way, the backend and UI stay **unchanged** when moving from Phase A to Phase B — only this one line gets switched once a checkpoint exists on the VM.
- **Frontend:** a small, self-contained web UI with:
  - Timeline/play button: replay the real scene (intersection outline + moving points/icons per object class)
  - "Generate variant" button: calls `VariantGenerator.generate()` (the mock in Phase A, the real model in Phase B) — indistinguishable for the UI
  - **Stretch:** a simple interaction control ("pedestrian crosses anyway" / "vehicle brakes harder") as controllable generation
  - **Stretch:** an embedded short generated video clip (Cosmos API, see section 3) as a visual preview of the bigger vision from the main plan
- **Keep dependencies cleanly separated:** maintain `requirements-cpu.txt` (laptop, CPU PyTorch, sufficient for Phase A) and `requirements-gpu.txt` (VM, CUDA PyTorch, for Phase B) as separate files, so the repo installs on both machines without modification.

## 6. Sprint plan with phase separation (example: 5 working days, compressible to 3)

### Phase A — laptop, no GPU (days 1–4)

1. **Day 1 — data:** TASI setup, data exploration, schema/coordinate-system clarification, extraction of short observation/prediction windows per interaction scene, clarify/reconstruct the map outline.
2. **Day 2 — model code:** implement the diffusion trajectory model (architecture + training script + sampling function) and the `MockVariantGenerator` implementation. Sanity-check the training script with tiny dummy data (1–2 iterations, CPU) — **no real training**.
3. **Day 3 — backend & UI:** FastAPI service with the swappable `VariantGenerator` interface (section 5), BEV animation (Play/Compare/Generate), wiring backend → UI, end-to-end test with `GENERATOR_MODE=mock`.
4. **Day 4 — polish & handoff:** clean up `requirements-cpu.txt` / `requirements-gpu.txt`, write the README with VM instructions (see Definition of Done below), curate 2–3 scenes for the later demo, prepare stretch-goal UI elements (control, video slot) even though they're not "live" yet without a real model/API.

**Definition of Done for Phase A** (stop and report afterward, don't continue on your own):
- App runs locally in the browser, Play/Compare/Generate fully work with `MockVariantGenerator`
- Training script is written and confirmed error-free via a dummy sanity check, but **not actually trained**
- `requirements-gpu.txt` is prepared but not installed/tested on the laptop (no GPU available)
- README contains a brief "VM guide": clone repo → `pip install -r requirements-gpu.txt` → start real training → set `GENERATOR_MODE=trained`

### Phase B — VM with 8× V100 (day 5, or later)

5. **Day 5 — training & polish:** clone the repo onto the VM, install `requirements-gpu.txt`, real training on one V100 (see section 3), set `GENERATOR_MODE=trained`, quantitative plausibility checks (collision rate, speed/acceleration distribution generated vs. real), final pitch preparation with real (instead of mock) results.

**If only 3 days remain for Phase A:** merge days 1+2 (smaller, simpler model), drop the stretch goals (interaction control, video clip) entirely, reduce the UI to "play the real scene + show one (mock) variant next to it." That's still a compelling, browser-runnable core message before even moving to the VM.

## 7. What the demo is meant to prove

- **For grant applications/reviewers:** technical proof that a generative traffic world model can be trained on real data collected at your own infrastructure, producing plausible, physically consistent scenario variants — as a solid foundation on which the bigger vehicle-perspective/Cosmos expansion (see the main plan) can be built.
- **For industry-partner conversations:** a tangible demonstration, understandable within minutes, of the core principle "learn from real infrastructure data, generate controllable synthetic scenario variants for testing/training purposes" — without needing the full pixel-video stack to convey the value.

## 8. Risks & fallbacks

- **Data volume:** a single Zenodo tag might be tight for a robust diffusion model. Fallback: a smaller model, stronger data augmentation (mirroring along the intersection axis, time shifting, crop sampling), or — if quickly accessible — supplementing with some of your internal additional data.
- **Map geometry:** if no clean HD map/OpenDRIVE file exists for the intersection: roughly estimate the intersection outline/lanes from the density of the real trajectories themselves (e.g. a convex hull per movement direction) instead of waiting for an exact map.
- **Time pressure:** secure the MVP first (real vs. one generated variant, even a static plot is enough in an emergency), only add interactivity and stretch goals if time remains.
- **Stretch-goal API:** if no usable Cosmos API quota is found or the setup eats too much time: drop the stretch goal outright without jeopardizing the demo's core — it's deliberately kept optional.
- **Phase mixing:** if a Claude Code instance accidentally tries to train anyway in Phase A (e.g. because "it would work on CPU too, just slowly") — explicitly abort that. Even a technically possible CPU training run on the real data would take days instead of hours and undermine the point of the phase separation.
